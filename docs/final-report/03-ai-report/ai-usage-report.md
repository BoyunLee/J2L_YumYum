# AI 사용 보고서

## 1. 사용 목적

YumYum 프로젝트에서 AI는 구현을 대체하기보다, 빠른 코드베이스 분석, 안정화 방향 도출, 문서 초안 작성, 발표자료 구성을 보조하는 도구로 사용했다. 최종 결정과 검증은 사람이 수행했고, 코드 변경 후에는 빌드와 정적 점검으로 결과를 확인했다.

## 2. 사용 AI/도구

| 도구 | 사용 목적 | 산출물 |
| --- | --- | --- |
| Codex | 코드베이스 분석, 안정화 구현, 문서 패키지 작성 | 설정 정리, provider 패턴, 설계문서/발표 프롬프트 |
| Chrome 제어 도구 | 프로젝트 일지 확인 | 개발 흐름과 의사결정 맥락 정리 |
| Gamma 등 외부 발표 AI | 발표자료 생성 예정 | 최종 PPT/PDF 초안 |
| Mermaid | 다이어그램 원본 작성 | Use-Case, ERD, 클래스, 시스템 구조, 간트 차트 |

## 3. 사용 원칙

| 원칙 | 적용 방식 |
| --- | --- |
| 비밀값 미입력 | OAuth secret, API key, JWT secret, 개인 토큰은 AI 입력에서 제외 |
| 사람 검토 | AI가 작성한 코드/문서는 사람이 diff, 빌드, 화면 기준으로 검수 |
| 구현 기준 문서화 | 실제 존재하는 화면, API, DB 테이블만 발표자료에 반영 |
| 초안 중심 활용 | 기획 정리, 구조화, 문장화에는 AI를 적극 사용하되 최종 판단은 팀이 수행 |
| 재현성 확보 | 사용한 대표 프롬프트를 `ai-prompts.md`에 기록 |

## 4. 사용 기능별 정리

| 구분 | 사용한 프롬프트/기능 | 활용 결과 | 사람 검증 |
| --- | --- | --- | --- |

| 구현 보조 | provider/repository 패턴, 설정 템플릿, FE API 전환 | 외부 API 장애 시 fallback 가능한 구조 | `npm run build`, `mvn -DskipTests compile` |

| 문서화 | 설계문서/PPT/AI 보고서 구조화 | 최종 산출물 패키지 초안 | 제출 기준 이미지와 항목 대조 |

## 5. 주요 AI 활용 사례

### 5.1 코드베이스 맥락 파악

- 입력: “프로젝트 전반과 Git 커밋로그를 스캔해서 컨텍스트로 가져보자”
- 결과: 현재 스택, 최근 기능 흐름, Docker/OAuth/추천/식단 구현 상태 파악
- 활용: 데모 MVP 안정화 계획의 근거로 사용

### 5.2 프로젝트 일지 학습

- 입력: “5월 22일부터 6월 24일까지 일지를 읽고 학습해 컨텍스트에 포함”
- 결과: ERD/DDL, 화면 설계, OAuth/JWT, OCR/바코드, Docker 구성의 개발 흐름 정리
- 활용: 발표자료의 개발 과정, WBS, 참고 문서 작성에 반영

### 5.3 데모 MVP 안정화

- 입력: “YumYum 행사 데모 MVP 안정화 계획 구현”
- 결과: 환경 설정 템플릿, external provider 패턴, 추천 생성 API, FE 직접 GMS 호출 제거, 한글 메시지 정리
- 활용: 데모 중 외부 API 장애에도 mock 결과로 시연 가능한 구조 확보

### 5.4 최종 산출물 패키지 구성

- 입력: “설계문서 6개 항목, 발표용 PPT, AI 사용 보고서를 만들기 위한 목표 수립 및 구현”
- 결과: `docs/final-report/` 아래 설계문서, 발표 프롬프트, AI 보고서, 다이어그램 원본 구성
- 활용: Gamma 등 외부 AI에 바로 전달 가능한 자료 패키지 작성

## 6. 품질 관리 방식

- AI가 제안한 변경은 실제 파일 기준으로 검토했다.
- 빌드 가능한지 확인했다.
  - FrontEnd: `npm run build`
  - BackEnd: `mvn -q -DskipTests compile`
- 민감정보 검색을 수행해 API key, OAuth secret, token이 문서/로그에 노출되지 않도록 점검했다.
- 발표자료는 실제 구현된 화면과 API 흐름만 사용하도록 제한했다.

## 7. AI 산출물 검수 체크리스트

| 체크 항목 | 기준 |
| --- | --- |
| 사실성 | 실제 repo에 없는 기능, 화면, API가 추가되지 않았는가 |
| 보안 | secret, token, 개인 계정 정보가 포함되지 않았는가 |
| 일관성 | 프로젝트명, 기술 스택, 발표 흐름이 문서 전반에서 같은가 |
| 제출 기준 | 설계문서 6개 항목과 AI 사용 보고서가 모두 포함되었는가 |
| 발표 적합성 | 20분 발표 기준으로 과도한 기술 설명 없이 화면 중심으로 구성되었는가 |

## 8. 한계와 보완

- AI가 생성한 문서는 팀원 이름, 팀 사진, 개인 회고처럼 프로젝트 외부 정보를 알 수 없으므로 플레이스홀더로 남겼다.
- 외부 발표 AI가 만든 디자인은 사실관계가 틀릴 수 있으므로, 생성 후 반드시 슬라이드별 내용 검수가 필요하다.
- 보안상 실제 secret, token, 계정 정보는 AI 입력에 포함하지 않았다.
- OAuth redirect, 실제 운영 URL, 발표 당일 테스트 계정은 별도 운영 체크리스트에서 최종 확인해야 한다.

## 9. 발표자료에 넣을 요약 문장

“AI는 빠른 분석과 초안 작성에 활용했지만, 최종 구현과 검증은 코드베이스, 빌드 결과, 시연 흐름을 기준으로 사람이 확인했습니다. 특히 데모 안정성을 위해 외부 API를 직접 의존하지 않고 mock/live/fallback 전략으로 구조화했습니다.”
