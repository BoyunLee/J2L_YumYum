# 발표자 노트

## 전체 시간 배분

- 0:00~1:00 표지/소개
- 1:00~4:00 문제 정의와 목표
- 4:00~8:00 시스템 구조와 설계
- 8:00~13:00 핵심 구현 설명
- 13:00~18:00 시연 흐름
- 18:00~20:00 기대 효과, 개발 후기, AI 사용 보고

## 발표 운영 원칙

- 화면 시연 중 오류가 나면 기능을 계속 클릭하지 말고, 준비된 화면캡처로 전환해 흐름을 설명한다.
- “실제 OAuth 로그인”은 리허설 계정으로만 진행하고, 발표자료 캡처에는 실제 계정 정보가 없다고 설명한다.
- 외부 API 관련 질문에는 “기본값은 mock, 실제 키가 있을 때 live, 실패 시 fallback”이라는 정책을 반복해서 설명한다.
- 기술 설명은 구현 파일명을 나열하지 않고, 화면/데이터 흐름과 연결해 말한다.

## 슬라이드별 멘트

### 1. 표지

“YumYum은 냉장고 속 식재료를 식단 기록과 레시피 추천으로 연결하는 서비스입니다. 단순 재고 관리가 아니라, 오늘 무엇을 먹을지까지 이어지는 흐름을 목표로 했습니다.”

### 2. 목차

“발표는 기획 배경, 서비스 흐름, 설계와 구현, 시연, 회고 순서로 진행하겠습니다.”

### 3. 기획 배경과 문제 정의

“많은 사용자가 냉장고 속 재료를 정확히 기억하지 못하고, 유통기한이 지난 뒤에야 발견합니다. 또 식단 기록 앱과 냉장고 앱은 보통 분리되어 있어 보유 재료가 식사 결정으로 이어지지 않습니다.”

### 4. 서비스 목표와 핵심 흐름

“YumYum은 로그인 후 온보딩을 거쳐 재고를 등록하고, 식단을 기록하고, 보유 재료 기반 추천을 받는 흐름으로 설계했습니다.”

### 5. 경쟁 서비스 비교

“차별점은 냉장고 재고와 식단 기록을 연결했다는 점입니다. 여기에 OCR, 바코드, mock/fallback 전략을 붙여 데모와 운영 안정성을 높였습니다.”

### 6. 전체 시스템 구조

“프론트는 Vue/Vite, 백엔드는 Spring Boot와 MyBatis, DB는 MySQL입니다. OCR은 FastAPI 서비스로 분리했고, 외부 API는 provider/client 계층으로 감쌌습니다.”

### 7. DB/ERD

“핵심 도메인은 사용자, 냉장고, 식단, 레시피, 알림, 관리자입니다. ERD로 저장 구조를 설명하고, 클래스 다이어그램으로 controller-service-dao-provider가 어떻게 협력하는지 연결해서 보여드리겠습니다.”

### 8. 냉장고 등록

“등록 방식은 세 가지입니다. 수기 입력은 batch 구조로 여러 개를 한 번에 저장하고, OCR과 바코드는 분석 결과를 입력 폼에 자동 매핑하는 흐름입니다.”

### 9. 식단 기록

“식단 기록은 음식 검색, 항목 추가, 섭취량 입력, 저장, 일일 요약 갱신까지 한 화면에서 이어지도록 구성했습니다.”

### 10. 레시피 추천

“추천은 프론트가 외부 API를 직접 호출하지 않고 백엔드가 사용자 냉장고 재료를 읽어 생성합니다. `ConfigurableRecipeRecommendationProvider`가 mock, live, fallback을 선택하고, OCR/바코드도 같은 provider 경계 뒤에서 처리해 API 키가 없어도 시연이 멈추지 않습니다.”

### 11. 알림과 관리자

“알림은 유통기한과 공지 중심입니다. 관리자는 사용자 지표, API 사용량, 배치 이력, 공지 발송, 감사 로그를 확인할 수 있습니다.”

### 12. 시연 시나리오

“시연은 로그인, 온보딩, 냉장고 등록, 식단 기록, 추천 생성, 알림, 관리자 화면 순서로 진행합니다. 핵심은 한 사용자의 식재료가 추천과 알림까지 이어지는 흐름입니다.”

### 13. 기대 효과

“기대 효과는 음식물 낭비 감소, 식사 결정 시간 단축, 개인 식단 기록의 활용성 향상입니다. 향후에는 추천 품질과 운영 배포 안정성을 더 높일 수 있습니다.”

### 14. 개발 후기

“팀원별 역할과 회고를 소개합니다. 특히 외부 API를 직접 붙이는 것보다 장애를 전제로 fallback을 설계하는 것이 데모 안정성에 중요했습니다.”

### 15. AI 사용 보고

“AI는 코드 분석, 안정화 계획, provider 패턴 정리, 문서 초안과 발표자료 구성에 활용했습니다. 다만 모든 결과는 실제 빌드와 코드 기준으로 검증했습니다.”

## Q&A 대비 답변

| 질문 | 답변 방향 |
| --- | --- |
| 추천 결과가 항상 같은가요? | local/Docker 기본값은 안정적 시연을 위해 mock이며, live 모드에서는 실제 API를 호출하고 fallback 모드에서는 실패 시 mock 결과로 복구합니다. |
| OCR 정확도가 낮으면 어떻게 하나요? | OCR 결과는 바로 저장하지 않고 입력 폼에 후보로 채우므로 사용자가 검수 후 수정할 수 있습니다. |
| 개인정보와 토큰은 안전한가요? | 데모 문서와 캡처에는 더미 데이터만 사용했습니다. 운영 전에는 토큰 저장 구조를 HttpOnly cookie 기반으로 개선할 계획입니다. |
| 관리자 화면은 왜 필요한가요? | 외부 API 사용량, 배치 결과, 공지 발송 이력을 PM/운영자가 직접 확인하기 위한 안정성 장치입니다. |
